# Разработчикам бэкенда

## Как развернуть локально

### Необходимое ПО

Для запуска ПО вам понадобятся консольный Git и Make. Инструкции по их установке ищите на
официальных сайтах:

- [Git SCM](https://git-scm.com/)
- [GNU Make](https://www.gnu.org/software/make/)

Вы можете проверить, установлены ли эти программы с помощью команд:

```shell
$ git --version
git version 2.37.1.windows.1

$ make --version
GNU Make 4.4.1
Built for Windows32
<...>
```

#### Windows

Для тех, кто использует Windows, необходимы также программы **git** и **git bash**. В **git bash** необходимо
дополнительно установить **make**:

- Перейдите на сайт [ezwinports](https://sourceforge.net/projects/ezwinports/files/)
- Скачайте `make-4.4.1-without-guile-w32-bin.zip` (выберите версию без `guile`)
- Извлеките архив
- Скопируйте содержимое архива в папку `mingw64` или `ucrt64` внутри `C:\Program Files\Git\`
  (какая из них есть в вашей версии Git) **БЕЗ** перезаписи/замены любых вложенных файлов.
- Откройте новое окно **git bash** и проверьте установку командой `make --version`.

Все дальнейшие команды запускать из-под **git bash**.

### Создание виртуального окружения для работы с IDE

IDE для корректной работы подсказок необходимо развернуть виртуальное окружение со всеми установленными зависимостями.

В качестве пакетного менеджера в проекте используется [uv](https://docs.astral.sh/uv/).

[Установите uv](https://docs.astral.sh/uv/getting-started/installation/) и в корне репозитория выполните команду:

```shell
$ uv sync
```

[uv](https://docs.astral.sh/uv/) создаст виртуальное окружение `.venv`, установит необходимую версию Python
(проекту нужен Python 3.13) и все необходимые зависимости.

После этого активируйте виртуальное окружение в текущей сессии терминала:

```shell
$ source .venv/bin/activate      # Linux/macOS
$ source .venv/Scripts/activate  # Windows, Git Bash
```

Если не хотите активировать окружение, запускайте команды через `uv run`, например `uv run make lint`.

### Настройка pre-commit хуков

В репозитории используются хуки [pre-commit](https://pre-commit.com/), чтобы автоматически запускать линтеры
и другие проверки перед коммитом.

В корне репозитория в **активированном виртуальном окружении** запустите команду для настройки хуков:

```shell
$ pre-commit install
pre-commit installed at .git/hooks/pre-commit
```

В последующем при коммите автоматически будут запускаться проверки из
[.pre-commit-config.yaml](./.pre-commit-config.yaml):

- `check-added-large-files` — запрещает добавлять в репозиторий большие файлы;
- `editorconfig-checker` — проверяет файлы в `src/` на соответствие правилам из [.editorconfig](./.editorconfig);
- `ruff` — проверяет код в `src/` линтером.

Если проверки не пройдут, коммит прервётся с ошибкой.

Хуки используют программы из виртуального окружения, поэтому перед коммитом окружение должно быть активировано.

Запустить проверки вручную, без коммита:

```shell
$ pre-commit run --all-files
```

## Как вести разработку

Код проекта находится в папке `/src`.

Находясь в корневой директории проекта, запустить проект можно командой:

```shell
$ fastapi dev src/main.py
```

Проект будет работать по адресу http://127.0.0.1:8000/, интерактивная документация API — по адресу
http://127.0.0.1:8000/docs.

### Как установить python-пакет в виртуальное окружение

В качестве менеджера пакетов используется [uv](https://docs.astral.sh/uv/).

Вот пример, как добавить в зависимости библиотеку `beautifulsoup4`:

```shell
$ uv add beautifulsoup4
```

Конфигурационные файлы `pyproject.toml` и `uv.lock` обновятся автоматически.

Аналогичным образом можно удалять python-пакеты:

```shell
$ uv remove beautifulsoup4
```

Если необходимо обновить `uv.lock` вручную, то используйте команду:

```shell
$ uv lock
```

### Команды для быстрого запуска с помощью make

Для вывода списка часто используемых коротких команд используйте команду:

```shell
$ make help
```

### Как проверить код линтерами

```shell
$ make lint
```

Команда запускает `ruff check ./src`. Настройки линтера лежат в [ruff.toml](./ruff.toml).

### Как отформатировать код

```shell
$ make format
```

Команда запускает `ruff check --fix ./src` и автоматически исправляет то, что ruff умеет править:
сортировку импортов, лишние пробелы и т. п. После форматирования выполните `make lint`, чтобы убедиться,
что остались только те замечания, которые нужно исправить вручную.

## Как сделать коммит

Перед коммитом активируйте виртуальное окружение: хуки используют `ruff` и `ec` из него. Убедитесь, что хуки
установлены командой `pre-commit install` (см. [Настройка pre-commit хуков](#настройка-pre-commit-хуков)).

### Коммит с запуском pre-commit hooks

```shell
$ git status
$ git add <файлы>
$ git commit -m 'Описание изменений'
```

Перед созданием коммита автоматически запустятся `check-added-large-files`, `editorconfig-checker` и `ruff`.
Если все проверки прошли, коммит создан. Проверьте результат:

```shell
$ git log -1
```

### Коммит без запуска pre-commit

Подходит для правок, не затрагивающих код (например, документации). Сначала убедитесь, что изменён только нужный файл:

```shell
$ git status
$ git add CONTRIBUTING.md
$ git commit -m 'Update CONTRIBUTING.md' --no-verify
$ git log -1
```

Флаг `--no-verify` отключает хуки для этого коммита, линтеры не запускаются. Используйте его только в исключительных
случаях.

### Если линтеры не прошли

Коммит прервётся, ruff покажет файлы и строки с ошибками. Исправьте их:

```shell
$ make format   # автоматические исправления
$ make lint     # проверить, что осталось
$ git add .
$ git commit -m 'Описание изменений'
```

Ошибки, которые ruff не исправил сам, поправьте вручную по тексту сообщения.

### Если не прошёл editorconfig

Хук `editorconfig-checker` (`ec src/`) выводит файл и строку с нарушением: лишние пробелы в конце строки,
неверные отступы, отсутствие перевода строки в конце файла, неверные окончания строк. Исправьте нарушения по правилам
из [.editorconfig](./.editorconfig), затем снова выполните `git add` и `git commit`.

### Если в репозиторий пытается попасть большой файл

Хук `check-added-large-files` прервёт коммит, если в нём есть слишком большой файл. Уберите файл из коммита
(`git restore --staged <файл>`) и не храните такие файлы в репозитории.

### Файл .env

В `.env` лежат секреты (например, токен DeepSeek API), поэтому он не должен попадать в репозиторий. Убедитесь, что
файл указан в `.gitignore`:

```shell
$ git check-ignore -v .env
```

Перед каждым коммитом проверяйте `git status`: `.env` в списке изменений быть не должно.
